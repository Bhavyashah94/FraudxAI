# FraudxAI US Card Transactions — 100k, Synthetic, Boosted Fraud

100,000 synthetic payment-card transactions and five institutional views of the same batch,
generated by the [FraudxAI](https://github.com/Bhavyashah94/FraudxAI) discrete-event payment
simulator.

**This is synthetic data. No real cardholder, card number or merchant appears in it.**

| | |
|---|---|
| Rows | 100,000 per file (6 files) |
| Columns | 91 (main file) + 5 targeted views |
| Fraud label | `is_fraud`, 2,009 positives = **2.009%** |
| Time span | 2024-01-01 → 2024-02-16 = **46.91 days** (measured) |
| Currency | USD |
| Uncompressed | 601.4 MB → **60.9 MB** gzipped |
| License | Apache-2.0 |
| Generator | `fraudx 0.3.0`, region US, seed 42, commit `9895834` |

## Files

Every file has exactly 100,000 rows, one per transaction, keyed by `transaction_id`.

**Integrity — two manifests, because the two hosts store different bytes.** The files are
published gzipped; **Hugging Face stores them exactly as uploaded**, while **Kaggle
decompresses them** (a `.csv.gz` arrives as a plain `.csv`, 60.9 MB → 601.4 MB). The data
is identical either way — verified by downloading from both hosts and comparing SHA-256.
So verify with whichever matches what you downloaded:

```bash
sha256sum -c SHA256SUMS                    # the .csv.gz artifacts (Hugging Face)
sha256sum -c SHA256SUMS_UNCOMPRESSED.txt    # the decompressed .csv files (Kaggle)
```

Running the gzipped manifest against Kaggle's files will report them missing, because the
filenames differ — that is expected, not corruption.

The views are what an institution actually sees: the authorization feed (ISO 8583 messages,
response codes, AVS/CVV/3DS fields), the gateway's risk telemetry, clearing and settlement
presentment, the post-settlement dispute/chargeback ledger, and a threat-intelligence graph
of syndicate / botnet / mule identifiers.

## Intended use

- Training and stress-testing fraud detectors where the class is rare and the negatives are
  deliberately hard (sub-minute retries, velocity bursts, legitimate-looking fraud).
- Testing explainability and triage pipelines against a simulator that carries closed-form
  causal ground truth (`analytical_shapley_probability`, `dominant_causal_driver`,
  `counterfactual_twin`).
- Payment-rail plumbing tests: dual-message clearing, delayed labels, chargeback windows.

**Not intended for:** prevalence estimation, regulatory model validation, or any claim about
real-world fraud rates. See the caveats.

## Caveats you must read before using this data

### 1. Fraud prevalence is boosted ~12× above real card data

The dataset has **2.009%** fraud (`--fraud-rate 0.02`). For comparison, the real ULB
credit-card corpus (284,807 transactions), scored by this repository's own script, contains
**0.1727%** fraud; the literature reports card-fraud prevalence below ~0.2%. Resampling this
data to a realistic rate, or reporting metrics computed at 2%, will not transfer.

### 2. The time span is 46.91 days, not the 30 days requested

The export was generated with `--days 30`, but the measured span is
`2024-01-01T00:01:06 → 2024-02-16T21:55:23` = **46.91 days**. This section describes *this
published file*, whose span is a fixed property of the artefact.

**The cause has since been found and fixed in the generating repository.** `_get_card_hawkes_params`
divided each persona's transaction volume by a hard-coded constant — `55.0` for US — that
happened to equal *one persona's* volume rather than the population mean the scale is defined
relative to. The persona scales therefore averaged **1.1793** over the card population (a
realised mean volume of 64.86 against the 55.0 divisor), so every paced batch ran **~18% hot**
and landed well short of the requested span. Regenerating with the fix gives **29.80 days**
against the same `--days 30` (−0.7%), from 46.91 (+56.4%).

Two consequences for anyone using this file:

- **Reproducing this exact artefact requires the pre-fix commit.** A current checkout will
  regenerate a *different* stream. This file's checksums are pinned in `SHA256SUMS` and do
  not change.
- **Do not treat the span as evidence of a modelling choice.** It was a normalisation bug,
  not a deliberate horizon, and it is no longer present in the generator.

If you need a specific horizon, measure the span of whatever you generate rather than
trusting the flag alone — at small batch sizes the per-card first-arrival offset still
dominates, and fraud-driven card freezing extends the span further (see caveat 1 and the
repository's defect notes).

### 3. `dispute_recovery.csv` carries the label — do not join it into features

`is_fraud` appears in the main file *and* in `dispute_recovery.csv`. The dispute ledger is a
**post-settlement** view: it exists only after a chargeback has been filed, so it is
outcome, not input. Joining it into a feature set is direct label leakage. The repository's
leakage gate scopes the pre-settlement surfaces to `auth_stream` and `gateway_telemetry`
only (`spec/07_export_leakage_gate.yaml`).

### 4. The generator is **NOT CERTIFIED** by its own benchmark

Run under the evaluation protocol pinned in `spec/18_benchmark_reporting.yaml`
(`-n 2000 --seed 42`, five pinned seeds), the four-pillar certification benchmark returns
`NON_CERTIFIED_FAIL` in 5/5 seeds. Of the nine gates that fail, three fail in every seed
(inter-arrival Wasserstein, MCC Jensen-Shannon divergence, relative attribution error) and
**six flip with the seed** — a violation count quoted from one run is therefore not a
result. Reproduce with `fraudx benchmark -n 2000 --unified --seed 42`.

### 5. The amount gate grades resemblance to a hardcoded reference, not to real data

Pillar 1 compares this data against a fixed reference distribution
(US: `lognormal(μ=3.75, σ=0.85)` USD) rather than against a real corpus. Measured with
`scripts/score_external_corpus.py`:

| corpus | log10(1+amount) W₁ | log10(1+Δt s) W₁ | verdict |
|---|---|---|---|
| **this dataset (100k)** | **0.1312** PASS | **0.1460** PASS | PASS |
| reference-sampler control (n=1500) | 0.0000 PASS | 0.0016 PASS | PASS |
| real ULB corpus (284,807) | 0.3745 FAIL | 0.1716 FAIL | FAIL |

Real card data **fails** this gate while this synthetic data passes it, so the gate ranks
resemblance to the hardcoded reference — not resemblance to real card traffic. Also note the
clocks differ (smallest inter-arrival: ours 0.01 s, ULB 1 s), so the inter-arrival gate
partly measures timestamp resolution.

## Reproducing this dataset

```bash
git clone https://github.com/Bhavyashah94/FraudxAI && cd FraudxAI
python -m fraudx_synthesizer.cli generate -n 100000 --region US --seed 42 \
  --days 30 --fraud-rate 0.02 --export-institutional-views \
  -o fraudxai_us_100k_seed42.csv
# ~1 m 35 s; recorded with python 3.12.15, fraudx 0.3.0, commit 9895834
sha256sum -c SHA256SUMS_UNCOMPRESSED.txt   # the export is written uncompressed
```

Reproducing the measurement in caveat 5 (exact-command reproduction checked against the
published scorecard):

```bash
python scripts/score_external_corpus.py \
  --csv fraudxai_us_100k_seed42.csv \
  --amount-col amount --time-col tx_time_seconds --time-unit seconds --label-col is_fraud \
  --ulb corpora/creditcard.arff --reference-control 1500 \
  --json scorecard.json
```

Reproducing the certification status in caveat 4:

```bash
python -m fraudx_synthesizer.cli benchmark -n 2000 --unified --seed 42 \
  --output-dir reports/benchmark
```
